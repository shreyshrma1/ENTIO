# Phase 11.5+: Deterministic Compilation Of Connected Document Models

## Status

Implemented and verified on 2026-07-30.

This specification extends the implemented Phase 11.5 document-analysis pipeline.
It does not change the Phase 11 upload, extraction, evidence, authorization,
review, proposal, apply, reload, rollback, or applied-provenance foundations.

The Phase 11.5+ ExecPlan was completed after this specification and is
authoritative for delivery order, affected files, implementation slices,
verification commands, and stop conditions. This specification defines the
required product behavior and is aligned with those later planning decisions.

## Problem

Phase 11.5 reliably extracts document meaning, builds a connected model, checks
evidence, compares that model with the current ontology, and reaches human
review. Its final model stage still has two jobs:

1. decide what the ontology should mean; and
2. produce exact, ordered Entio operations.

The first job requires semantic judgment. The second requires exact knowledge of
Entio's typed operation contracts, temporary references, source rules, limits,
and dependency ordering. Combining the jobs causes useful semantic decisions to
be lost when the model formats an operation incorrectly. It can also encourage
the model to attach a property or rule to an unsuitable existing entity simply
because the correct supporting concept is missing.

Phase 11.5+ separates these responsibilities. The model produces a connected
semantic plan in product terms. Kotlin verifies that plan and deterministically
compiles the supported parts into Entio's existing typed operations.

## Goals

Phase 11.5+ will:

- make the final model stage describe intended meaning instead of low-level
  Entio operations;
- define a bounded, provider-neutral semantic-plan contract;
- preserve connections, evidence, rationale, critic findings, and provenance
  from the earlier analysis stages;
- compile supported classes, properties, hierarchy, individuals, assertions,
  and SHACL constraints deterministically in Kotlin;
- generate final IRIs, resolve references, order dependencies, prevent
  duplicates and collisions, and count expanded edits in Kotlin;
- keep unsupported or unsafe business rules visible as review-only findings;
- require a complete disposition for every verified discovery before review;
- report semantic coverage separately from compilation success;
- add compilation confidence without hiding weaker evidence, modeling, or
  ontology-fit confidence;
- improve consistency across repeated identical benchmark runs;
- reuse the existing private-draft, proposal, approval, apply, reload, and
  rollback workflow;
- preserve the rule that no ontology source changes before human approval.

## Non-Goals

Phase 11.5+ does not add:

- automatic acceptance, approval, application, or ontology writes;
- raw RDF, Turtle, SPARQL, or source-file instructions from the model;
- a second proposal, staging, or apply workflow;
- unrestricted agents, model loops, tools, or external retrieval;
- new RDF, OWL, or SHACL parsers or rule engines;
- new OWL or SHACL meanings that current approved typed operations cannot
  express;
- automatic creation of production individuals from illustrative examples;
- a semantic-plan editor or a second user-review step before recommendation
  review;
- a new database, queue, persistence layer, or durable workflow history;
- changes to upload, extraction, OCR, document formats, or temporary storage;
- document-ingestion features in the CLI or VS Code extension;
- silent model switching during a task.

The current phase-level boundaries and non-goals remain those in `AGENTS.md`.

## Proposed Behavior

### 1. Preserve The Existing Pipeline Up To Final Planning

Phase 11.5+ reuses verified discovery, connected modeling, reconciliation,
ontology alignment, and modeling critique. The active consolidated provider-call
shape may continue to combine responsibilities for cost control, but its
structured outputs must preserve those logical boundaries.

The work key continues to freeze documents, extraction versions, ontology and
current-work fingerprints, FIBO version, retained provenance, selected model,
and contract versions. A stale input blocks compilation and drafting.

### 2. Replace The Low-Level Final Plan With A Semantic Plan

The final model output contains semantic items and recommendation groups. It
must not contain final IRIs, `DocumentPlanOperationKind` values, operation DTOs,
source-write instructions, raw triples, or hand-authored dependency order.

Each semantic item contains:

- a stable task-local item ID;
- one supported semantic item kind;
- a plain-language label and optional definition;
- references to other semantic items or deterministic ontology-alignment
  matches;
- the verified discovery IDs and evidence IDs that support it;
- a rationale;
- a proposed outcome of executable, review-only, or blocked;
- unresolved ambiguity, when present;
- applicable critic-finding dispositions;
- evidence, modeling, and ontology-fit confidence.

The supported semantic item kinds are:

- class;
- object property;
- datatype property;
- individual;
- subclass relationship;
- object-property domain and range;
- datatype-property domain and datatype range;
- individual type;
- object-property assertion;
- datatype-value assertion;
- preferred label;
- definition;
- alternate label;
- supported node shape;
- supported property shape;
- supported SHACL constraint;
- complex rule.

Annotation-property creation and general annotation changes remain available
only when the semantic plan identifies an approved current typed pattern.
Deletion, broad revision, merge, split, and supersession meaning may reuse
existing typed operations only when the alignment result identifies exact
current entities and deterministic verification proves the mapping safe.
Otherwise those items are review-only or blocked.

### 3. Group Connected Meaning

The model groups items that form one understandable change. For example, a new
`Payment` class, a new `Payment Approval Record` class, and the property
connecting them normally belong to one group.

Groups contain semantic dependencies, not low-level operation dependencies.
Kotlin decides the final operation order. A group may be:

- **Executable** when every included item has a safe typed mapping;
- **Review-only** when it contains important meaning that cannot be executed;
- **Mixed** when a coherent executable structure and related review-only rule
  should be reviewed together;
- **Blocked** when evidence, ontology fit, references, limits, or safe mappings
  are insufficient.

The model may recommend a group boundary, but Kotlin may reject it or split it
only under the atomicity rules below.

### 4. Compile Supported Semantic Patterns In Kotlin

The deterministic compiler maps semantic items to existing typed Entio edits.
It does not invent RDF, OWL, or SHACL behavior.

The initial compilation patterns are:

| Semantic pattern | Compiled result |
| --- | --- |
| New class | Create class, then add label, definition, and supported superclass |
| New object property | Create property, then add label, definition, domain, and range |
| New datatype property | Create property, then add label, definition, domain, and datatype range |
| New individual | Create individual, assign a type, then add approved values and relationships |
| Subclass relationship | Add the supported superclass edit |
| Object assertion | Add an assertion between resolved individuals through a resolved object property |
| Datatype value | Add a supported literal value through a resolved datatype property |
| Required relationship | Create or update current supported node/property shapes and supported SHACL constraints |
| Supported threshold | Create or update a current typed numeric SHACL constraint only when it preserves the stated meaning |

The compiler must use the existing typed edit translators and semantic-web
libraries. It must not serialize raw RDF or create a parallel apply service.

### 5. Keep Unsafe Rules Review-Only

Separation-of-duty, aggregation, multi-record correlation, temporal, procedural,
and other complex rules remain review-only unless an already approved typed
SHACL operation can represent the complete intended meaning without distortion.

A threshold combined with a condition is not reduced to a simple minimum or
maximum constraint when that would change its meaning. Unsupported meaning
retains its evidence, rationale, critic context, related semantic items, and
confidence.

### 6. Resolve Existing And New Entities Deterministically

Semantic references can point to:

- an exact alignment result for a local, imported, current-work,
  prior-provenance, or pinned FIBO entity; or
- another semantic item in the same task.

Kotlin assigns temporary references and final IRIs. It validates entity kinds,
writable sources, namespace rules, collisions, duplicates, current-work
conflicts, and no-op changes. A model-provided label is never treated as a final
IRI.

Imported and FIBO entities remain read-only. Existing external-reuse behavior is
used where allowed; the compiler does not copy or modify external ontology
content.

### 7. Order Dependencies And Enforce Atomicity

Kotlin builds a dependency graph from semantic references and patterns.
Declarations precede labels, hierarchy, domain/range, type, assertions, and
constraints that depend on them. Cycles, unresolved references, incompatible
kinds, and forward-invalid dependencies block the affected group.

Limits are measured after semantic patterns expand into typed edits:

- no more than 20 expanded typed edits per atomic recommendation;
- no more than 100 expanded typed edits per task;
- no more than 100 final recommendations per task.

These are the existing approved Phase 11.5 limits.

An oversized group may be split only when:

- each result is independently coherent and valid;
- all dependencies needed by a result are included or already exist;
- applying one result cannot leave the ontology in a misleading partial state;
- review-only meaning stays attached to the most relevant result;
- the split order is deterministic and understandable.

If those conditions cannot be met, the group is blocked with an
`atomic-group-exceeds-limit` safe reason. Entio does not silently drop optional
meaning to fit a limit.

### 8. Add A Deterministic Completeness Gate

Every verified discovery receives exactly one final disposition:

- executable recommendation;
- review-only finding;
- matched to an existing ontology entity;
- merged into another discovery;
- duplicate;
- administrative metadata;
- illustrative example;
- rejected with rationale;
- unsupported;
- blocked.

The existing coverage ledger is extended where necessary to represent
`MatchedExisting` and `Blocked` explicitly.

An **important discovery** is any verified business-content discovery that is a
concept, individual, relationship, attribute, value, requirement, control,
conditional rule, conflict, ambiguity, or role. Administrative metadata is not
important. An illustrative example is important enough to require a disposition
but does not become executable without the existing individual confirmation
gate.

Missing, duplicate, unknown, or internally inconsistent dispositions block the
task before recommendation review. The benchmark manifest can additionally mark
named discoveries as required.

### 9. Report Two Separate Quality Measures

**Semantic coverage** measures whether required or important meaning was found
and given a valid disposition. Runtime reporting includes:

- important discoveries with a valid disposition divided by all important
  verified discoveries;
- benchmark required concepts, relationships, rules, individuals, and negative
  expectations reported as separate counts.

A disposition alone does not prove that a model is correct. Benchmark semantic
coverage therefore uses the expectation manifest and deterministic matching
rules, not only the model's own ledger.

**Compilation success** measures deterministic conversion:

```text
supported executable semantic items compiled into valid typed edits
divided by
all semantic items classified as supported and executable
```

Review-only and correctly blocked unsupported items are excluded from the
denominator. Items that claim to be executable but fail a supported pattern
count as compilation failures. Both numerator, denominator, percentage, and
safe failure counts are shown.

The measures remain separate. Neither is presented as a single overall task
quality score.

### 10. Extend Confidence Without Hiding Weakness

Recommendation confidence has four dimensions:

- evidence;
- modeling;
- ontology fit;
- compilation.

Overall confidence equals the weakest relevant dimension. Compilation
confidence is calculated by Kotlin:

- 100 when every executable item in the group compiles and all deterministic
  checks pass;
- a deterministic lower value when only an independently coherent subset
  compiles;
- 0 when an executable group cannot compile.

Review-only groups have no compilation confidence because compilation is not
applicable. Their overall confidence remains the weakest of evidence, modeling,
and ontology fit. The API represents “not applicable” explicitly rather than as
a misleading zero.

### 11. Incorporate Critic Findings

Every verified critic finding retains exactly one disposition:

- accepted and incorporated into the semantic plan;
- rejected with a plain-language rationale;
- unresolved.

An unresolved critic finding blocks the related group. Kotlin verifies the
ledger and the referenced semantic items. The compiler cannot erase or rewrite
a critic finding merely to make a group executable.

### 12. Present Compiled Recommendations For Human Review

The web review shows, for each group:

- the intended meaning in plain language;
- the exact compiled changes;
- executable, review-only, mixed, or blocked status;
- dependencies and generated final IRIs;
- evidence and provenance;
- critic findings and their dispositions;
- all four applicable confidence dimensions;
- semantic coverage and compilation results;
- validation, reasoning, SHACL, and semantic-diff previews;
- safe blockers.

The semantic plan is not a separate editable product surface in this phase.
Users accept, reject, or use already supported per-change review controls on the
compiled recommendation. Changing semantic meaning requires rejecting the
recommendation and rerunning analysis or using the ordinary ontology editing
workflow.

### 13. Preserve Review-Only Provenance Narrowly

When a mixed recommendation is successfully applied, related review-only
findings are retained in the existing applied document provenance record. This
allows later documents to confirm, revise, or challenge the unexecuted meaning.

A purely review-only recommendation remains temporary unless the reviewer
explicitly chooses **Retain as documented rule**. That action stores the
evidence-linked, non-executable finding in the existing durable document
provenance boundary without creating ontology edits. Rejected and unretained
review-only work remains temporary. This phase does not add a new persistence
layer or general automatic finding retention.

### 14. Keep Model Selection Explicit

A task uses the user's verified selected model for all provider-backed stages.
Entio never silently switches to a stronger model. Controlled benchmark runs
may compare the current model with another explicitly selected compatible model
using identical frozen inputs, prompts, limits, and scoring.

Model comparison reports semantic coverage, compilation success, prohibited
outputs, consistency, provider attempts, duration, and available usage or cost
data. A model change remains a user or product decision outside automatic task
execution.

## Inputs

### User Inputs

- the existing authorized project and document set;
- the verified selected provider model;
- existing analysis start, cancel, review, accept, reject, and individual
  confirmation actions.

No new raw-RDF, rule-language, source-write, or semantic-plan-edit input is
accepted.

### Existing Entio Inputs

- verified discoveries and evidence locations;
- connected model and reconciliation results;
- ontology alignment across local, imported, current-work, prior-provenance,
  and pinned FIBO scopes;
- critic findings;
- applied ontology and current-work fingerprints;
- writable ontology source metadata and namespace rules;
- existing typed ontology and SHACL edit capabilities;
- existing limits, proposal services, and applied document provenance.

### New Structured Inputs

- a versioned semantic-plan response;
- deterministic semantic-pattern definitions;
- the benchmark expectation manifest;
- compiler context containing exact entity identities, kinds, source
  permissions, fingerprints, and limits.

## Outputs

- a verified semantic plan;
- a complete discovery-disposition ledger;
- deterministic semantic coverage results;
- compiled atomic recommendation groups;
- final IRI and reference mappings;
- compilation success results and safe failure reasons;
- evidence, modeling, ontology-fit, compilation, and overall confidence;
- review-only and blocked findings with provenance;
- existing semantic diff, validation, reasoning, and SHACL previews;
- existing private-draft batches for accepted executable groups;
- stage records with semantic-plan and compiler contract versions and hashes.

Provider-specific request and response records remain inside the server adapter.
The browser receives only bounded, project-authorized DTOs.

## Validation Behavior

Validation occurs in this order:

1. validate the semantic-plan schema, size, IDs, enums, and bounds;
2. verify every discovery, evidence, alignment, and critic reference;
3. verify that every important discovery has one allowed disposition;
4. verify semantic item kinds and required reference roles;
5. classify each item against the approved pattern registry;
6. verify exact existing-entity kinds and writable-source rules;
7. build and validate the dependency graph;
8. generate collision-checked temporary references and final IRIs;
9. expand patterns and count typed edits;
10. split only dependency-safe oversized groups or block them;
11. translate through existing typed edit services;
12. reject duplicates, no-ops, stale inputs, and unsupported mappings;
13. run existing semantic diff, validation, reasoning, and SHACL previews;
14. calculate compilation results and confidence;
15. expose only verified recommendations for human review.

All sorting, IDs derived by Entio, reference resolution, operation ordering,
counts, and scores must be deterministic for the same verified input.

## Error Behavior

- Invalid provider JSON or an unknown semantic item kind fails the semantic-plan
  stage with a safe schema code and no partial plan.
- Missing evidence, discovery, alignment, or critic references block the
  affected plan; Entio does not guess.
- A stale ontology, current-work state, model binding, document set, prompt
  version, or prior-provenance snapshot blocks compilation and drafting.
- Unsupported semantic meaning becomes review-only when it is complete and
  evidence-backed; it becomes blocked when evidence or dependencies are
  insufficient.
- A bad domain, range, type, datatype, or assertion target blocks the affected
  group.
- Duplicate, collision, no-op, imported-write, and unresolved-reference errors
  use stable safe codes and do not expose provider or document secrets.
- An incomplete disposition ledger blocks final review.
- An unsafe oversized group is blocked rather than partially compiled.
- Cancellation stops remaining work and keeps ontology sources unchanged.
- Provider failure follows the existing bounded retry and correction rules. It
  does not create a model-controlled loop or fallback to the old operation
  planner.
- Any draft translation or proposal-preview failure leaves the review workspace
  intact and uses the existing atomic rollback behavior.

## Test Cases

### Semantic-Plan Contract

- Accept every supported semantic item kind with valid references.
- Reject final IRIs, raw triples, operation kinds, source-write instructions,
  unknown fields, duplicate IDs, and out-of-bound plans.
- Reject missing discovery, evidence, alignment, or critic references.
- Preserve deterministic order and hashes for equivalent inputs.

### Pattern Compilation

- Compile a connected class and object-property group.
- Create supporting classes before property domain and range edits.
- Compile a datatype property with a supported datatype range.
- Compile a subclass relationship.
- Compile an individual, its type, datatype value, and relationship assertion.
- Reuse a verified existing entity without creating a duplicate.
- Use existing external-reuse behavior without changing imported or FIBO
  sources.
- Compile preferred labels, definitions, and alternate labels through existing
  typed edits.

### SHACL And Complex Rules

- Compile a supported required-relationship constraint.
- Compile a supported standalone numeric threshold without changing its
  meaning.
- Keep conditional thresholds review-only when the condition cannot be
  represented safely.
- Keep separation-of-duty and linked-payment aggregation rules review-only.
- Reject unsupported SHACL forms and raw constraint text.

### References, Ordering, And Limits

- Resolve new-to-new and new-to-existing references deterministically.
- Reject cycles, unresolved references, wrong entity kinds, and bad domain or
  range targets.
- Generate stable, collision-checked IRIs.
- Prevent duplicate and no-op edits across applied and current work.
- Count expanded edits rather than semantic items.
- split a dependency-safe oversized group into coherent recommendations;
- block an oversized group that cannot be split safely;
- enforce 20 edits per recommendation, 100 edits per task, and 100
  recommendations per task.

### Completeness, Metrics, And Confidence

- Give every verified discovery exactly one disposition.
- Block a missing, duplicate, or invalid disposition.
- Exclude administrative metadata from the important-discovery denominator.
- Require a disposition and confirmation gate for illustrative individuals.
- Calculate semantic coverage counts and percentage deterministically.
- Calculate compilation numerator, denominator, percentage, and failures
  independently from semantic coverage.
- Treat compilation confidence as not applicable for review-only groups.
- Make overall confidence equal the weakest applicable dimension.
- Block unresolved critic findings.

### Review, Provenance, And Workflow

- Show intended meaning, compiled edits, generated IRIs, evidence, confidence,
  metrics, critique, and blockers in grouped review.
- Prevent the browser from constructing or changing compiled operations.
- Retain related review-only findings when a mixed recommendation is applied.
- Retain a pure review-only finding only after the reviewer explicitly chooses
  **Retain as documented rule**.
- Do not retain rejected or unretained review-only work durably.
- Preserve exact evidence locations and applied provenance.
- Require individual creation confirmation.
- Reuse private draft, proposal, approval, apply, reload, and rollback.
- Confirm that no source changes before approval or after failed verification.

### Permanent Benchmark

Using the two existing PDF fixtures, run ten identical frozen-input trials and
verify:

- required core concepts appear in at least 9 of 10 runs;
- required major relationships appear in at least 8 of 10 runs;
- at least 95% of supported executable semantic items compile;
- prohibited recommendations appear in 0 of 10 runs;
- unsupported complex rules remain review-only in 10 of 10 runs;
- exact provenance remains valid in 10 of 10 runs;
- every important discovery has a disposition;
- illustrative individuals remain gated;
- no ontology changes are applied automatically.

Required positive concepts include Payment, Account, Payment Instruction,
Payment Approval Record, Supporting Record, Invoice, Payment Destination,
Consumer Loan, Loan Servicing, Payment Suspense, Servicing Control, the
High-Value Approval Rule, and the Linked-Payment Aggregation Rule.

Required negative checks include:

- do not create Compliance Status from administrative metadata;
- do not create Customer to Loan as `has servicing compliance`;
- do not attach payment rules to Account because Payment is absent;
- do not model Account to Invoice as payment approval;
- do not execute unsupported linked-payment aggregation or
  separation-of-duty rules.

The permanent deterministic suite uses recorded structured fixtures. Controlled
real-provider benchmark runs are an explicit release gate. Missing credentials
do not block implementation or offline verification, but they block phase
completion unless the user explicitly approves a recorded waiver that explains
the missing evidence and residual risk. This specification does not grant an
automatic waiver.

## Acceptance Criteria

Phase 11.5+ is complete when:

1. The final provider contract returns semantic plans, not exact Entio
   operations or final IRIs.
2. Kotlin compiles every approved supported semantic pattern through existing
   typed edit services.
3. Supporting entities are created before their dependent properties,
   assertions, and constraints.
4. Temporary references, final IRIs, dependencies, duplicates, collisions,
   sources, and freshness are resolved deterministically.
5. Unsupported complex rules remain evidence-linked and review-only.
6. Every important verified discovery has exactly one valid disposition.
7. Semantic coverage and compilation success are calculated and shown
   separately.
8. Compilation confidence is Kotlin-owned and overall confidence uses the
   weakest applicable dimension.
9. Expanded edit counts enforce the existing 20-per-recommendation and
   100-per-task limits.
10. Oversized recommendations split only when each part is coherent and
    dependency-safe.
11. Grouped review clearly shows intended meaning, exact compiled changes,
    evidence, critique, confidence, metrics, and blockers.
12. Related review-only findings enter applied provenance with a successfully
    applied mixed recommendation, while a pure review-only finding is retained
    only after the reviewer chooses **Retain as documented rule**.
13. Existing private-draft, proposal, approval, apply, reload, and rollback
    services are reused.
14. No ontology source changes before explicit human approval.
15. The permanent fixtures meet the approved repeated-run targets, or the user
    explicitly approves and records a controlled-provider benchmark waiver when
    verified credentials are unavailable.
16. Existing validation, reasoning, SHACL, proposal, apply, reload, and
    rollback regression tests remain green.
17. No new module, persistence layer, autonomous agent, raw RDF path, CLI
    ingestion surface, or VS Code ingestion surface is added.

## Open Questions

No blocking product questions remain for the initial implementation plan.

The newer ExecPlan resolves delivery structure and requires its contract-audit
slice to confirm these implementation details without expanding scope:

- the exact current typed SHACL constraint variants that qualify for the
  initial pattern registry;
- whether the existing coverage DTO can be extended compatibly or requires a
  versioned replacement;
- which existing review DTO fields can be reused for generated IRI mappings and
  compilation metrics;
- the available provider usage fields for optional cost comparison.

If an audit answer would require raw RDF, unsupported rule execution, automatic
approval, a new persistence layer, or an autonomous model loop, that behavior
must be deferred and the planning documents amended explicitly.

## Boundary Check

- The requested scope explicitly extends the active Phase 11.5 document
  workflow and does not alter unrelated product surfaces.
- Kotlin remains authoritative for semantic checks and executable operations.
- Ktor remains responsible for provider orchestration and authorized web
  contracts.
- React remains responsible only for temporary presentation and review input.
- Existing RDF, OWL, and SHACL libraries and typed services are reused.
- No speculative module, framework, persistence layer, apply path, CLI surface,
  or VS Code surface is introduced.
