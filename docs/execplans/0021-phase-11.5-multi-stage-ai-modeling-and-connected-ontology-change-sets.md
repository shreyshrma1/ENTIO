# ExecPlan: Phase 11.5 Multi-Stage AI Modeling And Connected Ontology Change Sets

## Status

Implemented and verified on 2026-07-27.

Cost-control amendment implemented on 2026-07-29. This amendment supersedes the
older requirement for unconditional reconciliation, ontology-alignment,
modeling-critic, and final-planning provider calls. Their semantic
responsibilities remain required, but the active runtime sequence is:

```text
verified per-document discovery
→ connected cross-document semantic synthesis
→ ontology-aware recommendation planning with modeling review
→ deterministic verification
→ human review
```

Model consolidation runs only when synthesis input must be chunked. Transport
failures use bounded transport retry. Deterministic semantic rejection receives a
bounded correction call containing the exact safe error and prior invalid output.
The implementation slices below remain the historical delivery record; where a
slice says that a separate provider call is mandatory, this amendment is
authoritative.

The Phase 11.5 scope, feature spec, and this ExecPlan are implemented. The
contract audit is recorded in
`docs/decisions/phase-11.5-slice-0-contract-audit.md`, and the verified delivery
is summarized in `docs/phase-summaries/phase-11.5-summary.md`.

## Goal

Replace Phase 11's direct document-to-candidate analysis with a bounded sequence that first understands the documents, then builds and critiques a connected model, and only then prepares executable change sets.

The implementation path is:

```text
verified extracted text
→ per-document discovery
→ connected cross-document semantic synthesis
→ ontology-aware recommendation planning and modeling review
→ Kotlin verification
→ grouped human review
→ existing typed private-draft and proposal workflow
```

No Phase 11.5 component approves, applies, or writes ontology content directly.

## Current State

- Phase 11 document ingestion is implemented in `core-types`, `semantic-engine`, `web-server`, and `web-app`.
- Intake, extraction, OCR, temporary storage, authorization, task lifecycle, review, staging, applied provenance, and existing proposal integration are working foundations and are not being replaced.
- `DocumentAnalysisService` currently makes one analysis call per document and one cross-document comparison call.
- `OpenAiDocumentAnalysisClient` currently uses one strict candidate response schema. It asks the model for candidate categories, possible domain and range, confidence, and evidence in the same response.
- Kotlin verifies evidence and `DocumentOntologyMatcher` matches candidates after provider work, but the provider has already shaped discoveries toward isolated edit categories.
- `DocumentRecommendation` represents one main candidate and a small set of derived operations. It does not represent a complete connected model, a dependency graph between new entities, separate critic findings, a discovery coverage ledger, or three confidence dimensions.
- `DocumentRecommendationDraftTranslator` translates one recommendation at a time. It cannot resolve references among several new items in one atomic recommendation.
- Task progress reports broad analysis and matching stages rather than every specialized AI stage.
- The browser already shows evidence and exact draft previews, but it is organized around isolated recommendations and does not show connected dependencies, critic findings, review-only rules, or stage provenance.
- The two benchmark PDFs already exist under `examples/simple-ontology/documents/`; no duplicate copies are needed.
- Existing ingestion bounds include ten documents, sixty thousand prompt characters per call, a 120-second provider timeout, twenty provider calls, eight evidence references, one hundred accepted edits, and twenty edits per draft batch.

## Target State

- Discovery is ontology-independent and produces only verified observations.
- Task-level modeling can introduce missing supporting concepts and connect them before ontology alignment.
- Reconciliation explains duplicate, refining, conflicting, and superseding evidence without choosing a winner.
- Alignment compares the connected model with local, imported, current-work, prior-provenance, and FIBO scopes.
- A separate critic finds bad domain/range choices, metadata promotion, flattened complex rules, missing support, and weak confidence.
- The final plan groups dependent items into atomic recommendations, supports validated temporary references, and limits each recommendation to twenty expanded typed edits after deterministic translation.
- Kotlin owns the coverage ledger, reference graph, typed-operation checks, IRI generation, duplicate checks, source checks, freshness, diff, validation, reasoning, and SHACL impact.
- Review-only meaning remains visible instead of being forced into a wrong executable edit and is retained in durable provenance when related executable changes are applied.
- The browser explains each grouped recommendation in plain language, including exact changes, evidence, dependencies, critique, confidence, impact, and blockers.
- Accepted executable operations continue through the existing private-draft, proposal, approval, apply, reload, and rollback path.
- The old single-stage provider schema is removed after the new pipeline passes deterministic and controlled real-provider verification.

## Architecture And Ownership

### `core-types`

Own immutable, provider-neutral records for discoveries, connected model items, reconciliation, alignment, critic findings, final plans, temporary references, confidence dimensions, coverage dispositions, stage provenance, and grouped recommendation decisions.

These records must not depend on Ktor, React, provider SDKs, Jena, PDFBox, POI, or Tesseract.

### `semantic-engine`

Own deterministic evidence reuse, temporary-reference and dependency verification, canonical ontology/FIBO reference checks, duplicate and no-op prevention, coverage verification, confidence calculation, IRI resolution, atomic change-set translation, and reuse of existing validation, diff, reasoning, and SHACL services.

It must not call providers, read uploads, manage users, or write ontology sources.

### `web-server`

Own stage orchestration, selected-model binding, stage-specific prompts and strict provider schemas, bounded context assembly, calls and retries, cancellation, task status, temporary intermediate state, safe hashes, project/user authorization, web DTOs, and handoff to the existing staging service.

Provider-specific records remain behind the ingestion provider adapter.

### `web-app`

Own stage-progress presentation, grouped recommendation review, evidence navigation, visible confidence and critique, supported reviewer inputs, and navigation to existing proposal review.

It must not resolve references, decide matches, construct RDF, calculate confidence, or decide whether an operation is safe to exclude.

### Modules That Remain Unchanged

- `validation-engine` and `graph-diff` are reused through current semantic and proposal services.
- `shared` receives no product logic.
- `cli` and `vscode-extension` receive no Phase 11.5 feature surface.
- No new Gradle module, database, queue, vector store, framework, agent runtime, or apply path is added.

### Active Call-Budget Formula

For `D` documents:

```text
required initial calls =
D discovery calls
+ connected-model chunk calls
+ 1 model-consolidation call when chunking is used
+ 1 ontology-aware recommendation-planning call
```

A two-document task ordinarily uses four calls. A ten-document task remains
bounded by:

- up to 15 planned logical calls;
- 3 attempts for transient retries;
- bounded, finding-specific correction attempts that never restart completed
  discovery or synthesis work.

The current correction reserve has one exact use: rerun only the rejected
semantic-synthesis or recommendation-planning stage with the deterministic error
attached. A clarification that changes frozen discovery input requires a new task.

Before starting any call, Entio must confirm that enough attempts remain to complete all still-required stages. If the remaining budget is insufficient, the task stops with a clear bounded-limit result. Entio must not begin a reconsideration when doing so would prevent completion of required downstream stages.

## Large-Inventory Modeling

Verified discoveries must never be silently dropped.

When the verified discovery inventory cannot fit into one 60,000-character connected-model request:

1. partition discoveries deterministically into bounded chunks;
2. run one connected-model call per chunk;
3. run one bounded consolidation call over the chunk models;
4. verify that every discovery receives a final coverage disposition.

Chunk boundaries must preserve evidence references and must not split one discovery record. If the required chunk calls cannot fit within the task call budget, the task stops as incomplete before final planning.

## Temporary-Reference Contract

Temporary references use this grammar:

```text
new:<kind>:<localName>
```

Approved kinds are:

- `class`;
- `objectProperty`;
- `datatypeProperty`;
- `annotationProperty`;
- `individual`;
- `shape`.

Examples:

```text
new:class:Payment
new:class:PaymentApprovalRecord
new:objectProperty:hasApprovalRecord
new:individual:Payment902771
```

Rules:

- references are case-sensitive;
- each reference is unique within one final plan;
- `localName` uses ASCII letters, digits, and underscores and begins with a letter;
- labels are never references;
- declarations must appear before use;
- unresolved or kind-incompatible references fail verification;
- critic findings may recommend replacement or splitting, but only the final-plan stage creates the replacement temporary IDs;
- temporary IDs never become final IRIs;
- Kotlin resolves them to collision-checked final IRIs.

## Discovery Coverage Contract

Every verified discovery must receive exactly one final disposition:

- represented by an executable recommendation;
- represented by a review-only finding;
- merged into another discovery;
- duplicate;
- administrative metadata;
- illustrative example;
- unsupported;
- rejected with rationale.

A discovery without exactly one valid disposition blocks final planning.

## Critic-Finding Disposition

The critic produces findings only. It does not mutate modeling or alignment records.

The final-plan stage must assign each critic finding exactly one disposition:

- accepted and incorporated;
- rejected with a concise rationale;
- unresolved.

An unresolved critic finding blocks the affected recommendation.

## Recommendation Atomicity

Atomicity is measured using the expanded typed-edit count produced by deterministic translation, not the number of model plan items.

One atomic recommendation may contain no more than twenty expanded typed edits.

When a proposed recommendation would exceed that limit, the final-plan stage must split it into dependency-safe atomic recommendations. A split is valid only when each resulting recommendation is independently coherent and no required cross-recommendation dependency would permit partial invalid application.

Entio must not span one atomic recommendation across several existing draft batches.

## Reconciliation Inputs

Reconciliation compares all of the following:

- discovery to discovery;
- connected-model item to connected-model item;
- connected-model item to durable prior applied provenance.

It must preserve the distinction between raw evidence, modeled meaning, and previously applied ontology meaning.

## Benchmark Matching Rules

The benchmark evaluates meaning rather than exact labels alone.

An expected concept or relationship may pass through:

- the approved preferred label;
- an approved alternate label;
- reuse of an existing ontology entity with equivalent meaning;
- the required semantic category and relationship pattern.

Slice 0 must pin the accepted aliases and structural expectations for every benchmark item.

## Review-Only Rule Lifecycle

Review-only rules related to applied recommendations are retained in durable provenance.

They must:

- remain visible in proposal and apply history;
- be available to later document-reconciliation workflows;
- remain clearly marked as non-executable;
- never be written into ontology source files unless a later approved phase adds that behavior.

## Blocked Recommendation Behavior

When one operation invalidates a recommendation:

- the entire recommendation is blocked;
- all of its operations remain visible;
- valid operations are not silently extracted;
- the user may request a split or reconsideration;
- only the server-approved final-plan workflow may create new atomic recommendations;
- React must not perform dependency splitting.

## Phase 11 Path Retirement

During implementation, existing Phase 11 tasks and completed records remain readable.

After Phase 11.5 activation:

- all new ingestion tasks use only the Phase 11.5 multi-stage pipeline;
- there is no automatic or silent fallback to the Phase 11 single-stage path;
- incomplete legacy tasks may remain readable but cannot resume through the new pipeline;
- the old single-stage production execution path and provider schema are removed after Phase 11.5 verification passes;
- durable Phase 11 provenance remains readable.

## Rollback Notes

- Every slice is a separate branch and focused commit so it can be reverted without discarding unrelated work.
- Slices 1–7 add contracts and isolated stage behavior but do not replace the production orchestrator until Slice 8.
- Before Slice 8, rollback leaves the existing Phase 11 path active.
- Slice 8 switches to the new pipeline and retires the old provider schema. Rollback must revert the switch and the associated stage contracts together; it must not delete durable Phase 11 provenance.
- Slice 9 reuses current staging. Reverting it removes connected-plan translation only, not shared staging or proposal behavior.
- Slice 10 is additive presentation and can be reverted without changing stored applied provenance.
- Temporary tasks and intermediate stage results are not durable and require no migration rollback.
- Applied provenance extensions must use compatible decoding. A rollback may ignore new optional fields but must keep existing records readable.
- Applied ontology changes remain ordinary Entio proposals and continue to rely on existing reload and rollback behavior.

## Risks And Assumptions

- More calls increase latency and provider cost. The fixed formula, reserved retry/reconsideration attempts, prompt limits, and pre-call completion-budget checks are mandatory.
- Using the same model as both author and critic is not fully independent. Separate prompts, structured findings, deterministic verification, and human review reduce but do not remove that risk.
- A coverage ledger requires one final disposition for every verified discovery and prevents silent downstream loss, but it cannot prove that discovery itself was complete.
- Structured output can still be conceptually wrong. The critic and reviewer remain necessary.
- Current typed SHACL cannot express many policy rules. Those rules must remain review-only rather than being approximated.
- Connected recommendations may expand into more typed edits than their plan-item count suggests. Atomicity is capped at twenty expanded typed edits; larger proposals must be split into dependency-safe recommendations before staging or remain blocked.
- The existing ontology snapshot is bounded. Alignment must disclose truncation and block unsupported certainty rather than pretending it saw the complete graph.
- Model quality varies. Deterministic fixtures prove orchestration and guards; the controlled real-provider benchmark evaluates practical quality separately.
- In-memory task state means deployment invalidates incomplete Phase 11.5 work. This is accepted and must remain clear in the UI.
- Existing uncommitted user files or unrelated work must be preserved during every slice according to `AGENTS.md`.
