# Phase 11.5: Multi-Stage AI Modeling And Connected Ontology Change Sets

## Status

Implemented and verified on 2026-07-27.

The more recently updated Phase 11.5 ExecPlan is authoritative for delivery order, limits, and implementation boundaries. This spec is aligned with those decisions.

Amended on 2026-07-29 after throughput testing showed that the separate
reconciliation, alignment, critic, and final-planning calls repeatedly transmitted
the same large verified context. The active pipeline preserves those
responsibilities while consolidating them into connected semantic synthesis and
one ontology-aware recommendation-planning call. Deterministic validation may
request one bounded, finding-specific correction; it does not cause unconditional
self-critique calls.

## Problem

Phase 11 can extract documents, verify quoted evidence, compare candidates with the current ontology, and send accepted typed changes through Entio's existing review workflow. Its analysis contract, however, asks the model to identify document meaning and shape it into edit-like candidates too early.

That early commitment causes predictable modeling errors. When a needed concept is absent, the model may attach a property to an unrelated existing class. It may treat document-control fields as business meaning, turn a conditional policy into a simple data field, omit supporting concepts, or return several isolated edits that do not form a usable model.

Phase 11.5 replaces that single-stage analysis with specialized model
responsibilities. The model first records what each document says, then synthesizes
a connected cross-document model, and finally compares that model with Entio's
current ontology while reviewing modeling quality and preparing bounded change
sets. Kotlin verifies the structured outputs and every executable operation. A
person still decides what enters the private draft and what is ultimately
approved.

## Goals

Phase 11.5 will:

- separate document understanding from ontology editing;
- use bounded calls for discovery, connected semantic synthesis, and ontology-aware recommendation planning;
- let the model identify useful concepts and rules even when Entio cannot yet execute them;
- produce connected recommendations with ordered, dependent operations;
- let new operations refer to other new items through temporary IDs;
- include ontology structure, individuals, and business facts;
- preserve complex rules as review-only findings when current typed edits cannot express them safely;
- distinguish administrative metadata from business meaning;
- classify individuals as illustrative, production, ambiguous, or unknown;
- show evidence, modeling, and ontology-fit confidence separately;
- verify evidence, references, dependencies, supported operations, duplicates, sources, and graph freshness deterministically;
- show every stage's progress, timing, model, prompt version, and safe failure;
- keep all executable changes in the existing private-draft and human-approval workflow;
- permanently test the two existing Phase 11 example PDFs against known positive and negative expectations.

## Non-Goals

Phase 11.5 does not add:

- automatic acceptance, approval, or application;
- direct RDF, Turtle, SPARQL, ontology-source, or SHACL-source generation;
- a second proposal or apply path;
- unrestricted agents, model loops, tools, or external retrieval;
- model authority over evidence validation, duplicate checks, ontology validity, or approval;
- new OWL or SHACL meanings beyond Entio's current typed operations;
- automatic creation of production individuals from policy examples;
- durable storage for uploads, extracted documents, incomplete tasks, or complete intermediate model responses;
- CLI or VS Code document-ingestion surfaces;
- changes to the ordinary native ontology assistant;
- a claim that deterministic checks can prove a modeling judgment is conceptually correct.

## Proposed Behavior

### 1. Keep The Existing Phase 11 Boundary

Phase 11.5 reuses the implemented Phase 11 workflow for:

- project-scoped upload and temporary storage;
- PDF, DOCX, TXT, and Markdown extraction;
- exact evidence locations and OCR confidence;
- the current user's verified selected OpenAI model;
- local, imported, current-work, prior-provenance, and FIBO context;
- task authorization, cancellation, deletion, and safe progress;
- recommendation review and evidence viewing;
- conversion to existing typed ontology and SHACL edits;
- private staging, preview, diff, validation, reasoning, SHACL checking, proposal review, approval, atomic apply, reload, and rollback;
- durable provenance for successfully applied document-derived changes.

The public task, evidence, decision, and draft routes remain project scoped. Their responses may gain Phase 11.5 fields, but no new route may write ontology sources or bypass the existing review path.

Existing Phase 11 tasks and completed records remain readable during implementation. After Phase 11.5 activation, incomplete legacy tasks cannot resume through the new pipeline, all new tasks use only the Phase 11.5 pipeline, and there is no automatic fallback to the old single-stage path. Durable Phase 11 applied-provenance records remain readable and usable during alignment.

### 2. Freeze The Analysis Inputs

At analysis start, the server records a work key containing:

- project and task IDs;
- document checksums and metadata;
- extractor version;
- current applied ontology fingerprint;
- private draft, shared staging, and current proposal fingerprints;
- pinned FIBO package version;
- prior-provenance snapshot hash;
- selected provider and model ID;
- every stage's prompt and response schema version.

The selected model is fixed for the task. Entio does not silently switch models between stages. If the model selection, ontology state, current work, documents, prompt versions, or relevant prior provenance changes, downstream results are stale and cannot be drafted.

### 3. Run A Bounded Consolidated Pipeline

The initial pipeline uses these logical model calls:

1. one discovery call for each document;
2. one or more connected semantic-synthesis calls over deterministic discovery chunks;
3. one model-consolidation call when more than one synthesis chunk is needed;
4. one ontology-aware recommendation-planning call for the task.

For `D` documents, the required initial calls are:

```text
D discovery calls
+ connected-model chunk calls
+ 1 model-consolidation call when chunking is used
+ 1 ontology-aware recommendation-planning call
```

A two-document task ordinarily uses four calls. A ten-document task may use up
to fifteen planned logical calls. The synthesis stage compares documents, and
recommendation planning receives bounded durable prior provenance even when a
task contains only one document.

There is no model-controlled loop. Later stages receive bounded, verified outputs from earlier stages rather than unrestricted conversation history or complete raw documents.

Each provider response receives immediate schema, size, identifier, and reference checks. Discovery evidence is also checked against server-held extracted text before it can reach modeling. The complete structural and semantic verification runs after final planning.

The approved prompt, request-schema, and response-schema versions are:

| Stage | Prompt version | Request schema | Response schema |
| --- | --- | --- | --- |
| Discovery | `phase-11-5-document-discovery-v2` | `phase-11-5-document-discovery-request-v2` | `phase-11-5-document-discovery-response-v2` |
| Connected modeling | `phase-11-5-connected-model-v1` | `phase-11-5-connected-model-request-v1` | `phase-11-5-connected-model-response-v1` |
| Model consolidation | `phase-11-5-model-consolidation-v1` | `phase-11-5-model-consolidation-request-v1` | `phase-11-5-model-consolidation-response-v1` |
| Reconciliation | `phase-11-5-reconciliation-v1` | `phase-11-5-reconciliation-request-v1` | `phase-11-5-reconciliation-response-v1` |
| Ontology alignment | `phase-11-5-ontology-alignment-v1` | `phase-11-5-ontology-alignment-request-v1` | `phase-11-5-ontology-alignment-response-v1` |
| Modeling critic | `phase-11-5-modeling-critic-v1` | `phase-11-5-modeling-critic-request-v1` | `phase-11-5-modeling-critic-response-v1` |
| Final planning | `phase-11-5-final-plan-v1` | `phase-11-5-final-plan-request-v1` | `phase-11-5-final-plan-response-v1` |

The consolidation call is conditional and uses a separate contract from connected
modeling. Deterministic verification is a Kotlin stage and makes no provider call.

Stage input packing is deterministic and records which upstream records were included. Entio does not silently sample or discard verified discoveries to fit a later prompt. A discovery call records included and omitted block counts; any omitted document block makes the analysis incomplete and prevents draft creation. When the complete verified discovery inventory cannot fit one connected-model request, Entio partitions whole discovery records into deterministic chunks, models each chunk, and consolidates the chunk models. If the required calls cannot fit the task budget, the task stops as incomplete before final planning.

### 4. Discover Document Meaning Without Drafting Edits

Each document discovery call receives:

- bounded located-text blocks from that document;
- document authority and applicability metadata;
- opaque document and block IDs;
- no ontology context.

Keeping ontology context out of discovery prevents the current model from narrowing its observations to concepts that already exist.

The response is a discovery inventory. Each item has:

- a unique discovery ID;
- a kind: concept, definition, individual, relationship, attribute, value, requirement, control, conditional rule, conflict, ambiguity, or metadata;
- a content classification: business content or administrative metadata;
- an assertion classification: explicit fact, implied fact, model interpretation, or illustrative example;
- a concise neutral description;
- exact evidence references;
- related discovery IDs;
- evidence confidence;
- an individual classification when the item identifies a person, organization, account, loan, invoice, payment, or other possible individual.

Discovery produces no typed ontology operation, target IRI, source choice, domain, range, or final recommendation.

Kotlin verifies each evidence reference and exact quotation. An item with invented or altered evidence is rejected. Rejected discoveries remain visible in safe stage counts but do not enter later stages.

### 5. Build A Connected Domain Model

The connected-model stage receives all verified discovery inventories, including their classifications and evidence IDs. It does not receive ontology matches. It uses one bounded call when the inventory fits or deterministic chunk calls followed by one bounded consolidation call when needed. Chunk boundaries preserve whole discovery records and evidence references.

It may propose:

- classes and class hierarchy;
- object and datatype properties;
- suitable domain and range;
- individuals, types, assertions, and values;
- constraints;
- supporting concepts needed by another relationship;
- complex rules that may remain review-only.

The output is one consolidated connected model, not an executable plan. It may introduce model-local references so a new property can point to a newly proposed class. Every class, property, domain, range, assertion, and constraint includes a short rationale and links back to discovery IDs.

Administrative metadata may remain in the model only when it describes the document itself. It must not be promoted to the business ontology merely because it has a label and value.

### 6. Reconcile Documents And Prior Evidence

The reconciliation call receives:

- verified discoveries;
- the connected model;
- bounded authority, applicability, date, jurisdiction, product, and business-unit metadata;
- bounded summaries of durable prior provenance.

It identifies duplicate meanings, alternate labels, supporting evidence, refinements, conflicts, supersession claims, and context-specific interpretations.

Reconciliation compares discovery to discovery, connected-model item to connected-model item, and connected-model item to durable prior applied provenance. It preserves the difference between raw evidence, modeled meaning, and previously applied ontology meaning.

This stage owns cross-document conflict detection and explanation. It does not resolve a conflict. It may recommend alternatives, but the final plan must mark unresolved conflicts for human review. A newer date alone never establishes authority or supersession.

### 7. Align The Model With The Current Ontology

The alignment call receives an Entio-built, bounded snapshot of:

1. applied local ontology entities;
2. imported ontology entities;
3. the current user's private draft;
4. shared staged work;
5. the current proposal;
6. other modeled items in this task;
7. durable prior provenance;
8. approved pinned FIBO results.

For each modeled item, the model recommends one of:

- reuse;
- extend;
- revise;
- create;
- split;
- merge;
- conflict review;
- leave unchanged;
- unsupported.

Alignment happens after connected modeling so the absence of `Payment`, for example, does not force a payment rule onto `Account`.

The model's match choice is advisory. Kotlin resolves every existing source, entity, and FIBO reference, performs canonical duplicate checks, and provides the deterministic match set used for review.

### 8. Critique The Proposed Model

The critic is a separate model call with a separate prompt and response contract. It may use the same task-selected model as the earlier stages; Phase 11.5 does not require a second model or credential.

The critic receives discoveries, the connected model, reconciliation results, alignment results, and the bounded ontology snapshot. It checks:

- whether evidence supports each meaning;
- whether domain and range are sensible;
- whether metadata was mistaken for a business concept;
- whether conditional rules were flattened into inappropriate properties;
- whether supporting classes or relationships are missing;
- whether illustrative examples are marked correctly;
- whether reuse, split, merge, revision, and confidence choices are justified.

Each critic finding targets a modeled item or planned recommendation and uses one of:

- approve;
- revise;
- split;
- replace;
- downgrade;
- reject;
- request clarification.

The critic is advisory. It cannot mutate an earlier result or approve an ontology change. The final planner assigns every critic finding exactly one disposition:

- accepted and incorporated;
- rejected with a concise rationale;
- unresolved.

An unresolved finding blocks the affected recommendation.

### 9. Produce A Final Connected Change-Set Plan

The final-planning call receives all verified stage outputs plus any bounded user clarification. It returns grouped recommendations.

Each recommendation contains:

- a stable recommendation ID and title;
- a plain-language description of the modeled change;
- discovery and evidence references;
- rationale and expected ontology impact;
- alignment choice and target source when relevant;
- zero or more ordered executable operations;
- zero or more review-only findings;
- operation dependencies;
- critic findings and their disposition;
- evidence, modeling, ontology-fit, and overall confidence;
- an executable, review-only, blocked, or mixed status.

A recommendation may expand to no more than twenty typed edits after deterministic translation. Across the whole final plan, there may be no more than one hundred expanded typed edits and one hundred recommendations.

Executable operations within one recommendation are atomic. Entio must not span one atomic recommendation across several existing draft batches. When a recommendation would expand beyond twenty typed edits, the final-plan stage must split it into independently coherent, dependency-safe atomic recommendations or leave it blocked. A reviewer may request a split or reconsideration, but only the server-owned final-plan workflow creates replacement recommendations. React never divides dependencies itself.

### 10. Use Temporary References Safely

New items use this exact temporary-ID format:

```text
new:<kind>:<localName>
```

Allowed kinds are:

- `class`;
- `objectProperty`;
- `datatypeProperty`;
- `annotationProperty`;
- `individual`;
- `shape`.

`<localName>` is case-sensitive, begins with an ASCII letter, and otherwise contains only ASCII letters, digits, and underscores. Examples are `new:class:Payment`, `new:objectProperty:hasApprovalRecord`, and `new:individual:Payment902771`.

Temporary IDs:

- are unique within one final plan;
- may reference only a declaration in the same plan;
- may not shadow or contain an existing IRI;
- are references in their own right; labels are never treated as references;
- must be declared before a dependent operation;
- must form an acyclic dependency graph;
- may be replaced or split only by the final-plan stage after critic advice;
- never leave the final-plan and draft-preparation boundary.

Kotlin assigns final IRIs through Entio's existing collision-checked IRI generation. It resolves all temporary references before constructing typed edits. An unresolved, duplicate, forward-invalid, cyclic, or kind-incompatible reference blocks the complete recommendation.

### 11. Separate Executable And Review-Only Meaning

Executable ontology operations are limited to Entio's existing typed operations for:

- classes, object properties, datatype properties, annotation properties, and individuals;
- labels, alternate labels, definitions, and supported annotations;
- superclass, type, domain, and range;
- object-property and datatype-value assertions;
- approved FIBO reuse.

Executable SHACL operations are limited to the current typed SHACL contract:

- create a node shape;
- create a property shape;
- update or remove a supported constraint;
- update a shape label;
- delete a shape;
- `MinCount`, `MaxCount`, `Datatype`, `Class`, `MinInclusive`, `MaxInclusive`, and `Pattern` constraints.

Anything requiring conjunction across records, aggregation, temporal sequencing, role separation, conditional applicability across several facts, unsupported SHACL, unsupported OWL, or raw RDF remains review-only.

Review-only findings appear beside the executable part of their recommendation with a clear reason they cannot be staged. When related executable changes are applied, the review-only findings are retained in durable provenance, remain visible in proposal and apply history, and are available to later reconciliation. They remain explicitly non-executable and are never written to ontology source files. A standalone review-only finding cannot enter the ontology proposal.

### 12. Treat Illustrative Individuals Explicitly

Every discovered possible individual has one classification:

- `Illustrative`;
- `Production`;
- `Ambiguous`;
- `Unknown`.

The model supplies the initial classification and rationale. Kotlin verifies that the value is present but does not decide whether the document describes a real production record.

An illustrative, ambiguous, or unknown individual is non-executable by default. Creating any document-derived individual requires a separate reviewer confirmation. The reviewer must also confirm changing an illustrative, ambiguous, or unknown classification to production. That decision is recorded in provenance.

### 13. Calculate Confidence Transparently

Every recommendation has integer scores from 0 to 100 for:

- evidence confidence;
- modeling confidence;
- ontology-fit confidence.

Kotlin calculates:

```text
overall confidence =
minimum(evidence confidence, modeling confidence, ontology-fit confidence)
```

The provider cannot supply a different overall value. The critic may recommend lowering a dimension but may not raise it. Any accepted critic downgrade becomes the final score. An unresolved confidence dispute blocks execution.

Confidence never grants approval. The existing low-confidence clarification rules continue to apply when overall confidence is below 60.

### 14. Measure Coverage Without Claiming Perfect Understanding

Kotlin builds a coverage ledger for every verified discovery.

Each discovery must receive exactly one final disposition:

- represented by an executable recommendation;
- represented by a review-only finding;
- merged into another discovery;
- duplicate;
- administrative metadata;
- illustrative example;
- unsupported;
- rejected with rationale.

Missing and conflicting dispositions fail final-plan verification. This check prevents silent loss between stages, but it does not claim that the model discovered every meaning in a document.

### 15. Verify Before Human Review And Drafting

Kotlin performs final-plan verification in this order:

1. response schema and numeric limits;
2. stage, model, prompt, input-hash, and output-hash provenance;
3. discovery coverage;
4. exact evidence and document locations;
5. existing ontology, source, prior-provenance, and FIBO references;
6. temporary-ID uniqueness, type compatibility, resolution, and dependency order;
7. critic finding disposition;
8. individual classification and confirmation gates;
9. supported typed ontology and SHACL operation mapping;
10. source writability and IRI collision checks;
11. canonical duplicate and no-op checks;
12. graph and current-work fingerprint freshness;
13. complete atomic recommendation preview;
14. semantic diff, deterministic validation, reasoning, and SHACL impact.

A failed executable operation blocks its whole recommendation. All of that recommendation's operations remain visible, and valid operations are not silently extracted. Valid recommendations elsewhere in the task remain reviewable. The user may request a split or reconsideration, but only the server-owned final-plan workflow may produce replacement atomic recommendations.

### 16. Present A Simpler Recommendation Review

The browser groups review by recommendation rather than showing disconnected candidate records.

Each card first shows:

- what Entio found;
- why it matters;
- exact proposed changes in dependency order;
- any meaning that is review-only;
- exact document provenance;
- critic concerns;
- the three confidence dimensions;
- expected impact and blocking issues.

Advanced match and source choices stay behind a clearly labeled details section. Raw provider JSON, temporary paths, and complete ontology snapshots never reach the browser.

The user can:

- accept or reject a recommendation;
- edit supported labels, definitions, values, target sources, and match choices;
- provide clarification;
- request one bounded reconsideration;
- rematch an item;
- request that the server split a recommendation;
- exclude an optional leaf operation when the server says it is safe;
- explicitly approve creation of an individual;
- submit accepted executable recommendations to the existing private draft.

### 17. Show Stage Progress And Provenance

Task progress uses these visible stages:

```text
Discovering document content
→ Building connected model
→ Reconciling documents
→ Aligning with ontology
→ Critiquing model
→ Preparing final change sets
→ Deterministic verification
→ Awaiting review
```

Each stage record includes:

- stage name and status;
- safe progress counts;
- start and finish time;
- duration;
- selected model ID;
- prompt and response schema versions;
- input and output SHA-256 hashes;
- provider attempt count;
- safe failure or retry code.

Raw prompts and complete provider responses remain in memory only for the running task and are not returned by list or progress routes. Logs contain IDs, hashes, counts, and safe codes, not document excerpts or provider payloads.

Cancellation stops the active request and prevents later stages from starting. Completed upstream results remain visible until task deletion but cannot be drafted from a cancelled task.

### 18. Bound Calls, Retries, And Reconsideration

Phase 11.5 uses these analysis limits:

| Limit | Value |
| --- | ---: |
| Documents | 10 per task |
| Discovery items | 200 per document and 2,000 per task |
| Connected-model items | 300 per task |
| Final recommendations | 100 per task |
| Expanded typed edits | 20 per atomic recommendation and 100 per task |
| Evidence blocks | 8 per recommendation |
| Planned logical calls | 15 for a ten-document task |
| Provider call attempts | 20 per task, including retries and reconsideration |
| Provider timeout | 120 seconds per attempt |
| Automatic retry reserve | 3 attempts per task |
| Reconsideration reserve | 2 attempts per task |
| Total analysis time | 30 minutes before awaiting review |
| Prompt size | 60,000 characters per call |
| Provider response size | 1,000,000 characters per call |

Before starting a call, Entio confirms that enough attempts remain for every required downstream stage. A transient retry reuses the exact frozen input and prompt version. One failed logical call receives no more than one exact-input retry unless Slice 0 approves a narrower rule. Authorization, validation, schema, evidence, and limit failures are not retried.

Users cannot arbitrarily rerun one failed stage. After the retry reserve is exhausted, the task fails safely and must be restarted. One review-time reconsideration uses exactly two logical calls: a reconsideration critic over the frozen alignment and one new final-plan call. The critic may advise a different final alignment choice, but discovery, connected modeling, reconciliation, and the alignment-stage record remain frozen. Entio starts this sequence only when both reserved attempts and the remaining completion budget are available. A clarification that changes document interpretation, connected modeling, reconciliation, or the alignment input requires a new task.

The existing Phase 11 file, page, extraction, OCR, temporary-storage, accepted-edit, and batch limits remain unchanged.

### 19. Preserve Only Necessary Intermediate State

Discovery inventories, model graphs, reconciliation results, alignments, critic findings, final plans, and complete prompt/provider payloads are temporary in-memory task data.

Durable applied provenance adds, when relevant:

- stage names;
- selected model ID;
- prompt and response schema versions;
- stage input and output hashes;
- final confidence dimensions;
- critic disposition IDs;
- coverage disposition IDs;
- related review-only findings for an applied recommendation.

It does not store complete prompts, complete responses, full documents, or unrelated review-only recommendations.

### 20. Retire The Single-Stage Analysis Contract

Phase 11.5 replaces `DocumentAnalysisService`'s direct candidate response and the matching single response schema with versioned stage-specific contracts.

The migration rules are:

- keep the existing project-scoped HTTP route family;
- keep existing document IDs, evidence IDs, task IDs, and applied-provenance records readable;
- add new task-stage and grouped-recommendation fields additively where practical;
- keep incomplete legacy tasks readable but do not resume them through the new pipeline;
- activate Phase 11.5 as the only path for new tasks after verification;
- retire the old production execution path, provider response schema, and prompt after the new end-to-end path passes;
- provide no automatic or silent fallback to the Phase 11 single-stage path;
- do not maintain two production analysis pipelines;
- continue to translate accepted final operations through the existing typed draft translator and staging service.

## Validation

### Stage Contract Validation

- stage and schema version are expected;
- counts and text lengths are within limits;
- all IDs use the correct scope and format;
- all references point to verified upstream records;
- input and output hashes match stored task records;
- no unknown fields or unsupported enum values are accepted.

### Evidence Validation

- document, page, block, and offset exist;
- excerpt exactly matches server-held extracted text;
- extraction and OCR metadata agree with the source block;
- low-confidence OCR gates remain in effect;
- evidence references are unique and bounded.

### Modeling Validation

- every model item traces to discoveries;
- administrative metadata cannot become an executable business edit without explicit business evidence;
- temporary references are unique, typed, declared, ordered, acyclic, and resolvable;
- domain and range have rationale and compatible reference kinds;
- every critic finding has a final disposition;
- every verified discovery has exactly one approved coverage outcome;
- overall confidence equals the weakest dimension.

### Executable Plan Validation

- each operation maps to an existing typed ontology or typed SHACL operation;
- target sources are current and writable;
- generated IRIs are valid and collision checked;
- canonical duplicate and no-op checks pass;
- atomic recommendation dependencies are complete;
- individual confirmation gates pass;
- graph and current-work fingerprints are current;
- semantic diff, validation, reasoning, and SHACL checks complete through existing services.

## Error Behavior

Failures use safe, stage-specific codes and plain-language messages.

- A malformed response envelope fails that stage. Within a schema-valid connected-model response, Entio performs one bounded finding-specific correction, then retains only deterministically valid items and records exact skip reasons for invalid items.
- If no connected-model item survives correction, final planning continues from the complete verified discovery inventory. Skipped provider items cannot create typed operations.
- If consolidation retains valid connected items but omits a document, Entio reports that document and uses its verified discoveries directly during final planning.
- Invalid discovery evidence removes the discovery from downstream input and records a count and reason. If no usable business discovery remains, the task stops before modeling.
- A timeout or transient provider failure receives at most one exact-input retry and is subject to the task retry and call budgets.
- An exhausted provider, authorization, schema, evidence, or limit failure stops the task safely.
- An unresolved temporary reference, cycle, unsupported operation, stale fingerprint, duplicate, or unwritable source blocks its full recommendation.
- An unresolved critic rejection, conflict, low confidence, or illustrative-individual decision marks the recommendation blocked or review-only.
- Cancellation ends the active call, starts no later call, creates no draft, and performs normal temporary cleanup.
- Valid recommendations remain visible when another recommendation fails deterministic verification, but failed operations are not silently omitted.
- No failure writes ontology source files or creates an approved proposal.

The UI shows the failed stage, safe reason, attempt count, and suggested user action. It does not show credentials, raw provider responses, hidden prompts, server paths, or unrelated document text.

## Test Cases

### Discovery

- finds concepts, definitions, relationships, controls, rules, individuals, and facts with exact evidence;
- distinguishes business content from document-control metadata;
- separates explicit facts, implied facts, model interpretations, and examples;
- rejects invented quotations and invalid offsets;
- records every valid discovery in the coverage ledger.

### Connected Modeling

- deterministically chunks an over-limit discovery inventory and consolidates the results without losing discovery coverage;
- blocks before final planning when the remaining call budget cannot complete chunking, consolidation, and downstream stages;
- proposes a missing supporting class before a dependent property;
- models `Payment`, `PaymentApprovalRecord`, their relationship, and supporting fields as one connected model;
- includes rationale for class, property, domain, and range;
- does not force a complex aggregation or role-separation rule into a data field;
- preserves unsupported meaning as review-only.

### Reconciliation And Alignment

- merges duplicate meanings and records alternate labels;
- preserves context-specific differences;
- surfaces conflict and explicit supersession without resolving them;
- reuses suitable local, imported, current-work, prior-provenance, and FIBO items;
- creates a new item when no correct match exists;
- does not attach a payment rule to `Account` merely because `Payment` is missing.

### Critique And Confidence

- rejects `Compliance Status` derived only from `Status: Approved`;
- rejects unsupported `Customer → Loan` servicing-compliance meaning;
- rejects incorrect `Account → Invoice` payment-approval modeling;
- lowers confidence for weak domain, range, or ontology fit;
- requires a disposition for every critic finding;
- calculates overall confidence as the minimum dimension.

### Temporary References And Atomic Plans

- accepts valid references between new classes, properties, shapes, and individuals;
- rejects duplicate, malformed, unknown, forward-invalid, cyclic, and kind-incompatible references;
- generates final IRIs only in Kotlin;
- preserves dependency order;
- validates one connected recommendation atomically;
- allows exclusion only for a safe optional leaf;
- revalidates a split recommendation.

### Individuals And Rules

- identifies core example people, organizations, accounts, loans, invoices, and payments;
- distinguishes illustrative from production data;
- requires explicit reviewer confirmation before individual creation;
- maps supported simple conditions to current typed SHACL constraints;
- keeps aggregation, sequencing, separation-of-duty, and multi-fact conditional rules review-only.

### Progress, Retry, And Security

- shows each stage, duration, model, prompt version, hashes, attempts, and safe status;
- cancels at every model stage;
- retries only a transient failure with identical input;
- enforces the twenty-attempt and thirty-minute task limits;
- marks omitted discovery input as incomplete and prevents it from producing a draft;
- reserves enough calls for required downstream stages before retry or reconsideration;
- refuses arbitrary single-stage reruns;
- invalidates downstream results when their inputs change;
- does not expose prompts, responses, paths, credentials, or unbounded ontology/document data.

## Acceptance Criteria

Phase 11.5 is complete when:

1. Document ingestion uses separate discovery, modeling, reconciliation, alignment, critique, and final-planning calls.
2. Discovery does not produce ontology edits or receive ontology context.
3. Connected modeling can introduce missing supporting concepts.
4. Final recommendations contain ordered atomic operation sets rather than isolated edits.
5. New items can reference each other through the specified temporary-ID format.
6. Kotlin rejects unresolved, cyclic, incompatible, duplicate, stale, or unsupported executable plans.
7. Administrative document metadata is visibly separate from business meaning.
8. Individuals are classified and require explicit approval before creation.
9. Unsupported complex rules remain visible and review-only.
10. Every verified discovery has exactly one deterministic coverage disposition.
11. The critic can revise, split, replace, downgrade, reject, or request clarification.
12. Every critic finding has a visible final disposition.
13. Evidence, modeling, ontology-fit, and weakest-value overall confidence are shown.
14. The review UI clearly presents what was found, exact changes, provenance, critique, confidence, and impact.
15. Each stage is bounded, visible, timed, cancellable, and recorded with model and prompt provenance.
16. Accepted executable recommendations use only the existing typed private-draft and proposal workflow.
17. No document-ingestion path writes ontology sources before human approval.
18. The two-PDF permanent benchmark passes every positive and negative expectation.
19. Existing Phase 11 applied provenance remains readable and useful for alignment.
20. Existing assistant, proposal, apply, reload, rollback, CLI, and VS Code behavior remains unchanged.
21. No atomic recommendation expands beyond twenty typed edits or spans several draft batches.
22. After activation, all new ingestion tasks use only Phase 11.5 and the old single-stage execution path is removed without a silent fallback.

## Open Questions

The Phase 11.5 scope questions are resolved as follows:

| Question | Decision |
| --- | --- |
| Which stages use separate calls? | Discovery uses one call per document. Connected modeling uses deterministic chunk calls plus consolidation when needed. Reconciliation, alignment, critic, and final planning each use their own call. |
| Can the critic use the same model? | Yes. It uses the same task-pinned model with a separate prompt and response contract. |
| What is the temporary-ID format? | The case-sensitive `new:<kind>:<localName>` grammar, kinds, and character rules defined above. |
| How many operations may one recommendation contain? | No more than twenty expanded typed edits, with no more than one hundred expanded typed edits per task. |
| Which SHACL rules are executable? | Only the seven constraint kinds and typed shape operations already supported by Entio. |
| How are review-only rules retained? | Related findings are retained in durable provenance when executable changes are applied and remain available to later reconciliation; standalone findings cannot enter an ontology proposal. |
| How are illustrative individuals represented? | By the required four-value classification plus explicit reviewer confirmation before creation. |
| How is completeness measured? | A deterministic coverage ledger gives every verified discovery exactly one approved disposition. |
| What if the critic disagrees? | The final plan marks the finding incorporated, rejected with rationale, or unresolved; unresolved findings block the recommendation. |
| Can a user rerun one failed stage? | No. Transient exact-input retries use the three-attempt reserve, with at most one retry for one failed logical call unless Slice 0 narrows the rule. |
| Who owns conflict resolution? | Reconciliation detects and explains; the human reviewer resolves. |
| How are prompts and intermediate results stored? | Versions and hashes may become provenance; complete prompts, responses, and intermediate records remain temporary in memory. |
| What is the overall confidence formula? | Kotlin takes the minimum of evidence, modeling, and ontology-fit confidence. |
| How is the Phase 11 contract retired? | Keep legacy tasks and durable provenance readable, prevent legacy tasks from resuming through Phase 11.5, activate the new pipeline as the only path for new tasks, and remove the old execution path and provider schema without fallback. |

There are no blocking product questions left in this draft. Implementation must stop if repository inspection shows that any resolved decision requires raw RDF, unsupported semantics, a second apply path, or a new durable workflow store.
